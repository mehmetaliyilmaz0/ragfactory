# Model refresh research — 2026-10-20

Provider documentation checked on 2026-10-20. Model IDs and lifecycle state below are provider-owned facts; “recommended default” is an implementation judgment balancing current availability, price/latency positioning, and the generic chat/embedding adapters used by ragfactory. Providers can change model availability quickly, so model IDs should remain user-configurable and this note should be rechecked before a release.

## API and lifecycle points that affect generated code

- OpenAI's GPT-6 family is available through current API SDKs. Its reasoning guidance says to use Responses for reasoning/tool use; GPT-6 Astra and GPT-6.1 Sol require Responses for tool calling, and GPT-6 Sol/Luna support Chat Completions function calling only with `reasoning_effort: "none"`. For non-`none` reasoning, remove `temperature`, `top_p`, and `top_logprobs`; Astra does not support custom temperature/top-p at all. This project does not expose a Responses API adapter yet, so current default generation should remain basic chat without tools and should omit temperature unless explicitly configured. See the [GPT-6 migration/parameter guide](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra) and [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist).
- Anthropic's current Python SDK and current model family have moved away from temperature sampling parameters: Anthropic says `temperature`, `top_p`, and `top_k` are deprecated on Opus 4.7+, non-default values produce 400 errors, and Python SDK v1 removes these request arguments. Generated Anthropic requests should omit temperature by default and only include it when the user explicitly sets one. See [deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations).
- Google model IDs must be migrated. `text-embedding-004` and legacy `embedding-001` are shut down; use `gemini-embedding-2`. The currently available `gemini-embedding-001` is distinct from the retired `embedding-001` name. See [Google's lifecycle table](https://ai.google.dev/gemini-api/docs/deprecations).
- Rerank is a separate endpoint/model family at Cohere and Voyage, not an embedding model. Cohere lists its V4 rerank models as live and documents automatic chunking for long documents; Voyage says the reranker is a second-stage relevance scorer after initial vector or lexical retrieval. See [Cohere model list](https://docs.cohere.com/v2/docs/models) and [Voyage reranker guide](https://docs.voyageai.com/docs/reranker).
- Cohere retrieval embeddings need `input_type="search_document"` for indexed passages and `input_type="search_query"` for searches. Current configuration exposes only one embedding input type, so callers must construct query and document encoders consistently or later split the setting by role. See [Cohere embedding guide](https://docs.cohere.com/docs/embeddings).
- Voyage retrieval embeddings should pass `input_type="document"` when indexing and `input_type="query"` at search time. All Voyage 4 family models share an embedding space. `voyage-3-lite` is a 512-dimensional legacy model (unlike Voyage 4 Lite, whose default is 1024), so its generator lookup must retain 512. Current template adapters do not expose per-call task choice, so default model dimension compatibility does not imply query/document role handling is correct. See [Voyage embeddings](https://docs.voyageai.com/docs/embeddings).
- Jina V5 uses the same JSON API style for embeddings and supports task selection and dimension truncation. Its model docs recommend a retrieval task adapter and say v5 Text Small handles 32K inputs natively; late chunking remains a Jina v3 feature for inputs beyond v3's 8K window. Keep the existing late-chunking path pinned to v3 rather than silently switching it to v5. See [Jina V5 API example](https://jina.ai/en-US/news/jina-embeddings-v5-text-distilling-4b-quality-into-sub-1b-multilingual-embeddings/) and [Jina v3 guide](https://jina.ai/en-US/models/jina-embeddings-v3/).

## Scope and limitations

This is a point-in-time provider-doc review, not a live API call or a benchmark. “Live” means the provider currently documents the model as available; it does not guarantee account entitlement, region support, rate limits, package integration compatibility, or stable vector-space quality. The project should keep accepting non-empty user-specified model IDs (with a conservative length bound), reject explicitly retired IDs with migration guidance, and fail dimension lookup for IDs whose dimensions are not verified. SDK constructor compatibility is being checked separately against the versions in this repository.

## LlamaIndex Google GenAI embedding adapter

For LlamaIndex, use `GoogleGenAIEmbedding` from `llama_index.embeddings.google_genai` and pass the selected ID via `model_name=...`. The package source defines that constructor argument directly, and its PyPI usage example uses the same import and keyword. The older `llama-index-embeddings-google` package is explicitly deprecated in favor of this integration. Sources: [LlamaIndex integration source](https://github.com/run-llama/llama_index/blob/main/llama-index-integrations/embeddings/llama-index-embeddings-google-genai/llama_index/embeddings/google_genai/base.py), [PyPI package usage](https://pypi.org/project/llama-index-embeddings-google-genai/), [deprecated Google integration](https://pypi.org/project/llama-index-embeddings-google/).

The source signature includes `model_name`, `api_key`, `embedding_config`, and `vertexai_config`; it resolves Google API credentials from `GOOGLE_API_KEY` or environment-detected Vertex AI configuration, so generated code can keep the model-only constructor. Constructor smoke testing should verify import and arguments without making a paid embedding request.
